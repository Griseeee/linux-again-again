# Лабораторная работа: Долгоиграющий процесс и обработка SIGHUP

## 1. Подготовка и запуск скрипта

Создал тестовый скрипт `alive.sh`:

```bash
cat << 'EOF' > alive.sh
#!/usr/bin/bash
while true; do
    echo "I am still alive"
    sleep 1
done
EOF

chmod +x alive.sh
```

По условию задания запускать утилитами вроде `nohup`, `tmux` или `screen` нельзя. Запускаю скрипт как обычный процесс в интерактивном режиме:

```bash
./alive.sh
```

Процесс начинает писать в терминал каждую секунду. Приостанавливаю его через `Ctrl+Z` (сигнал `SIGTSTP`), отправляю в фон командой `bg` и сохраняю его PID:

```bash
bg
pid=$(jobs -p %+)
echo $pid > alive.pid
```
Зафиксированный PID процесса: `14919`.

## 2. Защита процесса от закрытия терминала (SIGHUP)

Если сейчас просто закрыть SSH-сессию командой `exit`, процесс погибнет. 

### Что происходит при закрытии сессии:
1. SSH-сервер закрывает выделенный псевдотерминал (`/dev/pts/N`).
2. Командная оболочка (`bash`), являясь лидером сессии (Session Leader), ловит обрыв связи с терминалом и рассылает сигнал **`SIGHUP` (Signal 1 — Hangup)** всем дочерним процессам из своей таблицы заданий (`jobs`).
3. Действие сигнала `SIGHUP` по умолчанию — немедленное завершение процесса (`Terminate`).

### Как защитить уже запущенный процесс:
Защищаем процесс от отправки `SIGHUP` со стороны bash с помощью встроенной команды:

```bash
disown -h "$pid"
```

Флаг `-h` (*keep-hangup*) оставляет процесс в фоне, но выставляет в таблице заданий шелла метку: **не отправлять `SIGHUP` этому процессу при завершении сессии**. 

*(Второй способ сделать то же самое на уровне ядра — при подключении через GDB вызвать системный вызов `call (void)signal(1, 1)`, который меняет обработчик `SIGHUP` на `SIG_IGN` непосредственно в памяти процесса).*

## 3. Перенаправление потоков на лету через GDB (задание со звёздочкой)

Одного `disown` недостаточно: если оставить дескрипторы привязанными к `/dev/pts`, то при закрытии сессии следующая же попытка команды `echo` записать данные в несуществующий терминал вернёт ошибку ввода-вывода (`EIO`) или завершит процесс сигналом `SIGPIPE`.

Подключаемся к работающему процессу отладчиком `gdb` и на лету подменяем дескрипторы:

```bash
sudo gdb -q -nx -batch -p "$pid" \
  -ex 'call (int)close(0)' \
  -ex 'call (int)open("/dev/null", 0)' \
  -ex 'call (int)close(1)' \
  -ex 'call (int)open("stdout.log", 1089, 420)' \
  -ex 'call (int)close(2)' \
  -ex 'call (int)open("stderr.log", 1089, 420)'
```

Как это работает:
* Дескриптор `0` (`stdin`) уводим в `/dev/null`.
* Закрываем `close(1)`. По стандарту POSIX системный вызов `open()` всегда занимает наименьший свободный дескриптор. Поэтому следующий `open("stdout.log", ...)` гарантированно занимает номер `1`.
* Флаг `1089` — это битовая маска `O_WRONLY | O_CREAT | O_APPEND` (`1 | 64 | 1024`).
* Число `420` — восьмеричные права доступа `0644`.
* То же самое повторяем для дескриптора `2` (`stderr`).

Проверяем дескрипторы в `/proc`:

```bash
ls -l /proc/"$pid"/fd
```

Вывод:
```text
lr-x------ 1 root root 64 Oct 14 19:34 0 -> /dev/null
l-wx------ 1 root root 64 Oct 14 19:46 1 -> /root/stdout.log
l-wx------ 1 root root 64 Oct 14 19:40 2 -> /root/stderr.log
lr-x------ 1 root root 64 Oct 14 19:40 254 -> /root/alive.sh
```
Потоки успешно перенаправлены в файлы на диске, вывод в терминал прекратился.

## 4. Доказательство выживания процесса после отключения

Выходим из текущей сессии:

```bash
exit
```

Подключаемся заново по SSH и проверяем состояние процесса:

```bash
pid=$(cat alive.pid)
ps -p "$pid" -o pid,ppid,stat,tty,etime,args
```

Вывод:
```text
  PID  PPID STAT TT          ELAPSED COMMAND
14919     1 S    ?          00:18:24 /usr/bin/bash ./alive.sh
```

Что подтверждает выживание процесса:
1. **`PID = 14919`** — процесс не перезапускался, номер тот же.
2. **`TT = ?`** — процесс полностью отвязался от закрытого управляющего терминала `pts`.
3. **`PPID = 1`** — процесс перешёл под опеку `systemd`/`init` (демонизировался).
4. **`STAT = S`** — процесс жив и спит между итерациями (`sleep 1`).

## 5. Чтение потоков у работающего процесса

Проверяем запись в файл на лету:

```bash
tail -n 5 stdout.log
```

Вывод:
```text
I am still alive
I am still alive
I am still alive
I am still alive
I am still alive
```

Для непрерывного просмотра используем `tail -f stdout.log`. Новые строки стабильно появляются каждую секунду. Сам процесс при этом не прерывается. `stderr.log` создан и пуст, так как скрипт работает без ошибок.
