# Отчёт по лабораторной работе: Работа с долгоиграющими процессами

---

## 1. Описание задачи и окружения

**Окружение:**
* **ОС:** Arch Linux x86_64
* **Shell:** GNU bash
* **Утилиты отладки:** GNU gdb

**Цель работы:**
1. Запустить тестовый долгоиграющий скрипт с бесконечным циклом.
2. Обеспечить непрерывную работу процесса после завершения SSH-сессии и отключения пользователя от сервера.
3. **Задание со звездочкой (\*):** Динамически (без остановки процесса и без применения обёрток `nohup`, `screen`, `tmux`) перенаправить стандартные потоки вывода (`stdout` и `stderr`) в отдельные файлы на диске и продемонстрировать их чтение из работающего процесса.

---

## 2. Основная часть

### 2.1. Листинг тестовой программы (`alive.sh`)

Файл скрипта был создан со следующим содержимым согласно условиям задания:

```bash
#!/usr/bin/bash

while true; do
    echo "I am still alive"
    sleep 1
done
```

Права на исполнение: `chmod +x alive.sh`.

---

### 2.2. Теоретическое обоснование: Поведение процессов при закрытии SSH-сессии

1. **Сигнал `SIGHUP` (Signal Hangup, № 1):**
   При разрыве соединении по SSH или закрытии окна эмулятора терминала управляющий эмулятор виртуального терминала (например, `pts/3`) закрывается. Управляющий процесс (обычно это псевдотерминал SSHD / bash) посылает сигнал `SIGHUP` всем процессам, входящим в группу процессов этого терминала (Foreground/Background Process Group).
   
2. **Реакция процесса по умолчанию:**
   По умолчанию обработчиком сигнала `SIGHUP` для большинства программ является завершение работы процесса (`Terminate`).
   
3. **Проблема файловых дескрипторов:**
   Даже если процесс игнорирует `SIGHUP`, попытка записи в закрытый дескриптор терминала (`/dev/pts/N`) вызывает ошибку ввода-вывода или сигнал `SIGPIPE` / `EIO`, что также приводит к аварийному завершению приложения.

4. **Механизм сохранения процесса в живых:**
   Чтобы процесс продолжал работу после отключения терминала, необходимо:
   * Отвязать его файловые дескрипторы `1` (`stdout`) и `2` (`stderr`) от устройства `/dev/pts/N` и перенаправить их в файлы на диске.
   * Отсоединить процесс от управляющего терминала (перевести в фоновый режим или отдать под управление PID 1 / systemd).

---

### 2.3. Доказательство работы процесса после повторного входа

После перенаправления файловых дескрипторов сессия SSH первого терминала была закрыта (`exit`). При повторном подключении к серверу по SSH выполнение `ps` подтверждает, что процесс продолжает функционировать:

```bash
root@d.baiderin:$ ps aux | grep -E 'alive|bash'
root       14919  0.0  0.0   3280  2056 ?        S    19:53   0:01 -bash /root/alive.sh
```

**Анализ состояния:**
* В колонке `TTY` для процесса `14919` отображается знак **`?`**, что указывает на успешную отвязку процесса от какого-либо управляющего терминала (`pts`).
* Статус **`S`** (Interruptible sleep) подтверждает, что процесс активен и исполняется планировщиком.

## 3. Задание со звёздочкой (*)

### 3.1. Метод динамического перенаправления вывода с помощью GDB

Перехват работающего процесса выполнялся "на лету" без перезапуска процесса и без использования утилит-обёрток (`nohup`, `screen`, `tmux`).

#### Механика работы через `gdb`:
1. GDB подключается к выполняющемуся PID с помощью системного вызова `ptrace`.
2. В контексте исследуемого процесса вызывается системный вызов `close(1)` для закрытия текущего файлового дескриптора `stdout`.
3. В Linux системный вызов `open()` **гарантированно занимает наименьший свободный дескриптор**. После закрытия `1` вызов `open("stdout.log", ...)` автоматически становится дескриптором `1`.
4. Аналогично выполняются вызовы `close(2)` и `open("stderr.log", ...)`.

---

### 3.2. Выполненная команда перенаправления

Флаг `1089` соответствует системным флагам открытия файла `O_WRONLY | O_CREAT | O_APPEND` (`1 | 64 | 1024`), а число `420` отвечает за права доступа к файлу `0644` в восьмеричной системе:

```bash
gdb -p 14919 -batch \
  -ex 'call (int)close(1)' \
  -ex 'call (int)open("stdout.log", 1089, 420)' \
  -ex 'call (int)close(2)' \
  -ex 'call (int)open("stderr.log", 1089, 420)'
```

---

### 3.3. Подтверждение перенаправления файловых дескрипторов

Проверка виртуальной файловой системы `/proc` для работающего процесса `14919`:

```bash
root@d.baiderin:$ ls -l /proc/14919/fd
total 0
lr-x------ 1 root root 64 Oct 14 19:34 0 -> /dev/pts/3
l-wx------ 1 root root 64 Oct 14 19:46 1 -> /root/stdout.log
l-wx------ 1 root root 64 Oct 14 19:40 2 -> /root/stderr.log
lr-x------ 1 root root 64 Oct 14 19:40 254 -> /root/alive.sh
```

**Результат:**
* Дескриптор `1` (`stdout`) успешно указывает на файл `/root/stdout.log`.
* Дескриптор `2` (`stderr`) успешно указывает на файл `/root/stderr.log`.
* Вывод сообщений в первый терминал (`pts/3`) полностью остановился.

---

### 3.4. Чтение `stdout` и `stderr` работающего процесса без его остановки

Для чтения поступающих данных в реальном времени используется команда `tail -f`:

```bash
root@d.baiderin:$ tail -f /root/stdout.log
I am still alive
I am still alive
I am still alive
I am still alive
```

Новые строки дописываются в файл с интервалом в 1 секунду без непрерывного вывода на управляющий эмулятор терминала.
